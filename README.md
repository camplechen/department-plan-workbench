# 部门计划工作台

全中文、本地运行的部门计划与制定依据管理工作台。由管理员分配账号，无需外部服务或 API 密钥。编辑器及中文语言包均通过本地服务提供，运行时不访问 CDN。

## 下载与启动

适用于 Windows、macOS 和 Linux。需要先安装 Node.js 22.13 或更高版本，建议使用仍受支持的 LTS 版本；npm 随 Node.js 一起安装。无需 GitHub 账号、Git 或 API 密钥即可运行。

1. 在 GitHub 仓库页面点击绿色 **Code** 按钮，再选择 **Download ZIP**。
2. 完整解压 ZIP。不要在压缩包内直接运行，也不要直接双击 `public/index.html`。
3. 打开终端并进入解压后的项目目录。目录中应包含 `package.json` 和 `package-lock.json`：

   ```sh
   cd department-plan-workbench-main
   ```

   如果文件夹名称不同，请替换成实际名称；路径有空格时使用双引号包住路径。Windows 可在项目文件夹地址栏输入 `cmd` 并按回车，直接打开该目录的命令提示符。

4. 首次运行安装依赖：

   ```sh
   npm ci
   ```

   安装需要联网，会按照 `package-lock.json` 安装锁定版本，并自动生成本地编辑器、中文包和过滤模块。请使用完整命令，不要添加 `--omit=dev` 或 `--ignore-scripts`，构建需要开发依赖和安装脚本。

5. 启动项目：

   ```sh
   npm start
   ```

6. 保持终端运行，在浏览器访问 http://127.0.0.1:3210 。按终端的 **Ctrl+C** 停止服务。以后在同一目录运行 `npm start` 即可，可离线使用。

首次启动自动初始化管理员；业务数据为空（已有旧数据会自动迁移）。数据保存在运行服务的电脑上，同一工作台的已登录用户共享计划与依据。GitHub 仅分发源码，不保存或同步用户的业务数据。

### 常见启动问题

- 提示找不到 `npm`：安装 Node.js 后，关闭并重新打开终端，再执行 `node --version` 和 `npm --version` 检查。
- Windows PowerShell 阻止运行 `npm.ps1`：使用命令提示符（cmd），或将命令写为 `npm.cmd ci`、`npm.cmd start`，无需修改系统执行策略。
- 提示找不到 `package.json`：终端没有进入项目目录，先进入含该文件的文件夹。
- 安装失败：检查网络；修复后重新执行 `npm ci`。不要删除锁定文件来绕过错误。
- 页面或编辑器资源加载失败：确认 `npm ci` 已成功完成，通过服务地址访问页面。
- 提示 `EADDRINUSE`：3210 端口已被占用。先确认是否已启动本项目，或改用其他端口：

  macOS / Linux：

  ```sh
  PORT=3211 npm start
  ```

  Windows 命令提示符（cmd）：

  ```bat
  set PORT=3211
  npm start
  ```

  然后访问 http://127.0.0.1:3211 。服务只监听本机，不直接提供局域网多人访问。

## 升级

停止旧服务，先备份整个 `data` 目录，再将新版源码解压到新文件夹，将备份的整个 `data` 目录复制到新版目录，执行 `npm ci`、`npm start`，确认计划和图片正常后再处理旧目录。不要同时运行两个使用同一数据目录的服务。

## 登录与用户管理

打开 http://127.0.0.1:3210 时必须登录，没有自行注册入口。首次初始化的管理员账号与初始密码均为 `admin`；请在用户管理中设置自己的密码。此默认值仅用于初始化，之后启动不会覆盖已有密码或重新创建管理员。

- 管理员登录后进入侧栏「用户管理」，可新建用户、分配初始密码、编辑显示名称和角色、启用 / 停用、重置密码或删除用户。
- 「用户管理」包含「用户列表」和「组织架构管理」。组织支持多个顶级机构及多层下级机构，可新增下级、修改名称、调整上级和删除；不能将自身或下级设为上级，同一上级下不能重名。存在下级机构或归属用户（含停用用户）时禁止删除，须先调整关联。
- 新增、编辑用户时必须至少选择一个归属组织机构，支持同时选择多个分支及不同层级，例如同时归属「总部」「总部 / 运营部 / 一组」。勾选上级不会自动勾选下级，用户列表按完整路径显示每项归属。
- 升级后首次启动自动创建「默认机构」，将已有用户归入其中，保留原有账号、密码哈希、角色、状态及登录会话；管理员可随后调整归属或修改默认机构名称。后续启动不会覆盖已维护的组织架构和用户归属。新安装的初始管理员也归入默认机构。
- 组织架构及用户归属仅管理员可维护；机构归属用于记录人员组织关系，当前不会按机构隔离计划或依据的数据权限。
- 账号为 3 至 40 位字母、数字、点、下划线或连字符，创建后不可更名；密码为 4 至 128 个字符。密码经随机盐和 scrypt 哈希后存入 SQLite，不保存或返回明文。
- 登录后通过 HttpOnly、SameSite=Strict 的持久 Cookie 保持 30 天（自该次登录起算），无需每次重开浏览器重新输入；不把账号密码或令牌写入 localStorage。会话仅以令牌哈希存入 SQLite，因此重启服务后仍可识别。
- 点击右上角「退出登录」会删除当前会话并清除 Cookie，再次打开需登录。重置密码、停用、删除用户或调整角色会撤销该用户已有会话。
- 普通用户无法访问用户管理接口。当前所有已登录用户可共同查看、编辑全部计划和依据；详细的数据权限后续补充。删除用户不会删除已保存的计划或依据。
- 不允许删除或停用当前管理员，也不能取消自身管理员角色，确保仍可管理工作台。
- 计划 / 依据接口、图片上传及已上传图片读取均要求登录。页面和接口使用禁止缓存响应；浏览器清除 Cookie、隐私模式关闭或会话到期也会要求重新登录。

## 使用流程

1. 在「制定依据库」新建依据，填写分类、来源、日期和关键要求。
2. 点击依据行的「制定计划」，自动关联该依据；也可在计划页直接新建计划。
3. 填写部门、负责人、周期、目标与验收标准、行动安排；可多选关联依据。
4. 更新状态与进度。标记「已完成」时，进度自动保存为 100%。
5. 在「按依据查看」中按依据整理计划；未关联的计划单独展示。同一计划可在多个依据下出现。
6. 在依据详情中查看关联计划，点击计划名称查看详情。

支持新增、编辑、删除计划和依据；搜索、部门与状态筛选、逾期识别、概览统计，以及导出当前筛选结果为中文 CSV（可用 Excel 打开）。依据被引用时禁止删除，需先编辑关联计划解除关联。

## 计划富文本编辑

「新建 / 编辑计划」中的「目标与验收标准」（必填）和「行动安排 / 进展记录」使用本地 TinyMCE 8 社区版完整图文编辑器，中文菜单与工具栏包含：

- 图片：工具栏「图片」中选择本地文件、直接粘贴截图、拖拽图片进入正文；选中图片拖动缩放，或在图片属性中设置宽高，支持左 / 中 / 右对齐和文字环绕。
- 文字：字体、字号、加粗、斜体、下划线、删除线、文字颜色、背景高亮色、上下标。
- 段落：一至六级标题、四种对齐、行距、缩进 / 减少缩进、有序 / 无序列表、引用、分割线。
- 表格：插入表格，在「表格」菜单或右键菜单中增删行列、合并单元格等。
- 链接、清除格式、撤销 / 重做、全屏编辑；编辑弹窗加宽，两个编辑区各高 420px，可调整高度。

图片通过 `POST /api/uploads` 二进制上传到当前 `DATA_DIR` 的 `uploads/` 目录，默认 `data/uploads/`。单张最多 10MB，仅允许 PNG、JPG / JPEG、GIF、WebP，并校验文件头；服务端随机生成 UUID 文件名，不采用客户端路径或文件名。保存会等待图片上传完成，HTML 只保存 `/uploads/随机文件名.扩展名`，不保存 Base64、data 或 blob 地址。图片上传失败时会提示并阻止保存未上传的图片。已上传但未被引用的图片暂不自动清理，以免误删历史记录所用图片。

前后端共用 `sanitize-html` 白名单过滤：保存、读取和详情渲染均再次过滤，保留上述标签以及受限的字体、字号、颜色、背景色、对齐、行距、宽度、表格等样式；移除脚本、事件属性、任意定位、CSS 外部资源、嵌入对象和未知属性。图片仅允许本地上传地址，外部图片和 data 地址不入库；链接仅允许 http / https / mailto。内容安全策略禁止编辑器加载外部资源。粘贴文字使用编辑器自带过滤，最终保存仍经过统一白名单。

目标去掉标签、空白与零宽字符后为空时不可保存。计划详情按图文格式展示，点击图片可在新页查看原图；列表摘要、搜索和 CSV 导出使用纯文本。旧纯文本保留换行，上一版预设颜色自动兼容，无需数据迁移，读取不会改写历史数据文件。

安装后，编辑器静态资源生成在 `public/vendor/tinymce/`，包含中文包、插件、主题、皮肤和许可文件。修改 `src/rich-text.js` 或升级依赖后执行 `npm run build:vendor`；不要直接编辑生成的 `public/rich-text.js`。`package-lock.json` 锁定依赖版本。TinyMCE 社区版按 GPL-2.0-or-later 使用，中文包遵循相应 TinyMCE 许可，许可和声明随本地资源保留；对外分发时须遵守对应许可。

修改服务端代码后需重启服务，才能使新增路由与处理逻辑生效。

## 数据保存与备份

组织机构、用户及多机构归属、密码哈希、登录会话、计划、依据及关联关系统一保存在 `data/workbench.sqlite` 的 SQLite 数据表中，业务记录使用事务写入，不再写入 JSON 文件。图片保留在 `data/uploads/`，数据库只保存正文内的相对图片路径，不保存图片二进制或 Base64。可用 `DATA_DIR` 指定其他本地数据目录。

### 旧 JSON 数据迁移

升级前先停止旧服务并备份整个 `data` 目录。首次启动新版会读取旧 `data/workbench.json`，在一个事务中迁移计划、依据及关联，保留编号、时间和顺序。迁移成功后，原文件改名为 `workbench.json.migrated.bak`，仅作原始备份，不再读写或用于运行。后续启动不会重复导入。迁移失败会回滚并停止启动，保留原文件，不能通过删除数据库来绕过错误。

如果本来已有初始化完成的 SQLite 数据库，则以该数据库为准，不再次导入旧 JSON。不要同时运行旧版和新版服务操作同一个数据目录。

### 备份、恢复与回退

备份前停止服务，复制整个 `data` 目录；恢复前停止服务，将整个备份目录放回再启动。数据库和 `uploads/` 必须一起恢复，只恢复数据库会导致图片丢失。CSV 用于阅读交流，不是完整恢复文件。备份含用户及登录会话，应仅在本机妥善保存，不能上传 GitHub。

代码回退到旧 JSON 版不能直接读取新 SQLite 数据。需要同时恢复升级前的完整数据备份；回退后的旧版无法自动获得升级后新增的记录。迁移备份是升级时的快照，后续 SQLite 写入不会同步过去。

Node 服务只监听本机；云端使用 Nginx 在同机代理 HTTPS 入口，配置方式见下节。暂无审批流程、通用附件、提醒或云同步。多个页面同时编辑同一记录，以最后保存为准。业务内容不要录入外部平台密钥或密码；本工作台的登录密码由服务端专门哈希保存。页面不调用外部接口、字体或分析服务。

## 云服务器与 HTTPS 入口

可将一个 Node 进程、SQLite 和图片目录部署在同一台服务器上，通过 Nginx 提供 HTTPS。Node 继续监听 `127.0.0.1:3210`，公网仅开放网站所需的 80 / 443，数据库和图片目录不能配置为直接公开的静态目录。

- 在进程环境中设置 `APP_ORIGIN=https://workbench.example.com`（替换为自己的域名，无路径）。Nginx 负责 TLS；后端按这个明确配置校验浏览器 Origin，避免 HTTPS 页面被旧的 HTTP 来源校验拒绝。
- 当 `APP_ORIGIN` 为 HTTPS 时，登录和退出的会话 Cookie 均增加 `Secure`，只由浏览器通过 HTTPS 发送；`HttpOnly`、`SameSite=Strict` 和 30 天有效期保持不变。不会根据任意客户端传入的 `X-Forwarded-*` 头自动改变来源或 Cookie 策略。
- 未设置 `APP_ORIGIN` 时保留本机 HTTP 使用方式；配置含路径、查询参数、账号密码或非 HTTP 协议的地址会在打开数据库前报错退出。
- Nginx 代理到 `http://127.0.0.1:3210`，保留 Host，设置 `X-Forwarded-Proto`，上传大小限制至少设为 `12m`，使单张 10MB 图片可正常上传。不要将整个源码或数据目录作为网站根目录公开。
- 建议使用 systemd 启动，`ExecStart` 使用 Node 的绝对路径；通过 NVM 升级或移动 Node 后需要更新服务路径。服务环境配置 `NODE_ENV=production`、`PORT=3210`、`DATA_DIR=/var/lib/department-plan-workbench` 和自己的 `APP_ORIGIN`；数据目录只允许服务用户访问。
- 在公网开放应用前设置独立管理员密码；仅在 HTTPS 下通过浏览器登录。证书由 Nginx 使用，私钥只能保留在服务器本地，不能提交 Git 或发送到聊天。
- 更新前停止服务并备份完整 `DATA_DIR`；确认服务器工作区干净后 `git pull --ff-only`、`npm ci`，在独立临时目录执行 `npm test`，成功后重启 systemd 服务。不要覆盖或删除已有数据目录。

代码支持 HTTPS 代理不等于证书已部署；域名解析、证书申请和续期、Nginx / 系统防火墙配置及公网验收需在实际服务器上完成。当前架构采用单实例运行，共享 SQLite 文件的多节点部署不在本版本范围内。

## 项目结构

```text
department-plan-workbench/
├── package.json              启动与测试命令
├── server.js                 本地 HTTP 服务、校验与持久化接口
├── public/
│   ├── login.html / login.js  登录页面与会话入口
│   ├── index.html            中文页面与弹窗
│   ├── style.css             响应式界面样式
│   ├── app.js                计划与依据交互、筛选、导出
│   ├── rich-editor.js        本地 TinyMCE 初始化、图片上传与保存
│   ├── editor-content.css    编辑区内图文样式
│   ├── vendor/tinymce/       本地编辑器、中文包、插件及许可
│   └── rich-text.js          自动生成的前后端共用过滤模块、纯文本提取
├── src/database.js           SQLite 数据表、迁移、密码哈希与会话
├── src/rich-text.js          HTML 白名单过滤源码
├── scripts/build-vendor.mjs  本地资源复制和浏览器模块构建
├── data/uploads/             上传图片，需与业务数据一起备份
├── data/workbench.sqlite     首次启动自动创建的数据库
├── test/                    核心流程、持久化与富文本安全测试
└── README.md                 使用说明
```

执行 `npm test` 验证登录 / 退出 / 会话 / 用户管理 / 迁移及核心流程、图片上传 / 大小 / 类型 / 跨来源校验、资源路由、HTML 与 CSS 白名单、旧数据兼容及图文持久化。测试使用独立临时数据目录，不影响工作区数据。

## 开发协作

Codex 应用 / CLI 每次启动、重启或修改前，须重新阅读 `AGENTS.md`、完整 `CHANGELOG.md`、本说明、`package.json` 和相关源码，确认最新交接内容。普通使用者按上面的下载启动步骤操作即可。

### 维护者向 GitHub 同步改动

Codex 应用和 CLI 在完成每项调整后，按 `AGENTS.md` 进行检查、更新改动记录并提交源码；推送遵循用户当次指令，目前由用户操作，明确要求代为推送时才执行。需要在维护者电脑上配置好 `origin` 和 GitHub 推送认证，普通使用者无需这些配置。
